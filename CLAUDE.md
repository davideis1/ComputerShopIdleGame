# CLAUDE.md — Computer Shop Idle Game

Working notes for this project. **Keep this file up to date**: add a line to the Change log whenever a feature merges, and update the relevant section when architecture, balance numbers or conventions change.

## What this is
An idle shop game (desktop + mobile): run a computer shop from 1993 to today. Parody brand/product names only (never real ones). Start with name-brand prebuilts, later design and build custom PCs, sell games/accessories, consoles, hire buyers, franchise for tokens. Saving and offline progress are hard requirements. Hosted on PHP + MariaDB (user's host).

## Repo & workflow
- GitHub: `davideis1/ComputerShopIdleGame`, default branch **`Main`** (not master). Always branch off latest `origin/Main`.
- **No long-lived integration branch.** The native app (React Native + Expo in `app/`, simulation in `core/`) lives on `Main` like everything else. Branch each feature off the latest `origin/Main` and keep PRs small.
- **Stacking:** avoid stacking more than two PRs deep. If you do stack, open every PR against `Main` (not the branch below), merge them bottom-up with **"Create a merge commit" — never squash** (a squash rewrites the commits, so the next branch re-shows the earlier changes and conflicts). Don't delete a branch another open PR is based on.
- Work on a feature branch, push, open a **draft** PR against `Main`. If a stacked PR's base merges and its branch is deleted, GitHub closes it — rebase onto `Main` and open a new PR.
- **PR checks:** `.github/workflows/checks.yml` runs on every PR (game checks, a full `sim.js` run, `php -l`, app `tsc`); keep it green. New `tools/*-check.js` scripts should exit non-zero on failure and be added to its loop.
- Commit trailers: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` and `Claude-Session: <session url>`. PR bodies end with the "Generated with Claude Code" line + session URL.
- The user likes: a quick summary at the end, an offer to subscribe to the PR for review comments.

## Architecture notes
- **Client-side simulation**: vanilla JS, step-based; the same `step()` runs online and for offline catch-up (server time used for offline duration). State is a plain object (`E.newState/serialize/deserialize`); engine modules attach via `CS.*` hooks (`CS.M`, `CS.Con`, `CS.Advisor`).
- **Server limits:** `GAME_END_CAL` and `MAX_STATE_BYTES` in `inc/bootstrap.php` must fit what the game can produce; `tools/limits-check.js` (CI) compares them with `C.END_CAL` and a full-calendar save. When the calendar grew to 2035 the PHP limit stayed at Oct 2026 and every save past it was rejected (`out_of_range`) until 2026-10-26.
- **Saves**: server is source of truth with a `rev` check; `last_tab` column exempts same-tab reloads from conflict prompts; localStorage keeps a backup. Game data (parts, products…) stays in JS files — moving it into the DB was considered and deliberately skipped.
- **Calendar**: 420 s per game year (slowed from the original). Runs 1993 → Oct 2035 (`C.END_CAL` 42.8); "today" (Oct 2026, `C.TODAY_CAL` 33.8) is a milestone (trophy *Back to the Present*), after which the **Near Future** eras *Spatial Shift* (2027) and *Quantum Curious* (2031) carry on with speculative parts, PCs, add-ons, a console generation (Obelisk Spire, Nimbus Six, Orbitron Ring Visor, Hanami Hybrid 3), events and the `holo` theme. Near Future names are written final in the source files (no `names.js` rename needed, except the platform map, which needs every platform id).
- **Demand model**: 3 customer segments (budget .45 / main .40 / enthusiast .15) via `E.itemWeight(seg, rel, price, y, ref)`; purchase probability `min(.95, 1-exp(-tot/K))`, `K=0.8`; add-on attach scaled by `ADDON_SCALE=0.6`; games gated by PC capability (`pcRel`); console platform market shares + installed base; launch hype/allocation. Managers and the Designer reuse the same model (`modelRates`) to forecast.
- **Economy balance**: per-era payback derivation; add-ons and consoles each ~11–17% of revenue (target; add-ons now 14-18%, consoles 7-14%); `ADDON_SCALE` 0.5; Upsell Training +6%/level, max 20 (levels above a lowered max are clamped on load); token curve `floor(4*sqrt(R/1e8) - 3)` (R0 was 2e8 until prestige-pacing). Re-run `node tools/sim.js` after touching economy numbers and compare with the baseline.
- **`tools/sim.js`** loads the full `core/` and is seeded (`--seed=N`, default 1), so the same command prints the same numbers. `node tools/sim.js [minutes=330] [runs=1] [--bot=full|classic] [--stop=end|today|best|time] [--hq=ids] [--nohq=ids] [--quiet] [--items] [--save=FILE]`. A run ends when the calendar stops (Oct 2035) by default (`today` stops at Oct 2026, `best` keeps playing while the run's average tok/h still rises, `time` plays all minutes). `--save=FILE` writes the final save (seed the simulator with it for late-game screenshots). Between runs the bot claims and buys HQ upgrades in a fixed order (`--hq` puts ids first, `--nohq` skips them, handy for A/B: `--nohq=t_warp`). `full` (default) hires buyers + the PC Designer once the Purchasing Office opens and opens Console Corner; `classic` is the old hand-stocking bot. It ends with a table per franchise: minutes to 2000/2010/2020/today/2035, first claimable token, revenue, tokens, **tok/h** (tokens at the end / hours played, the prestige-pacing number) and revenue split (prebuilt / custom / PC add-ons / consoles incl. their games). Exits 1 if cash goes NaN, there's no revenue or the calendar stalls.
- **Baseline (2026-10-25, after more-restock, `node tools/sim.js 400 8`):** runs end at Oct 2035; length 300 → 218 → 194 → 186 → 182 → 182 → 180 → 180 min; tokens 25-42 per run; tok/h 5.4 → 14.0 (before the extra restock tiers: 4.0 → 8.6; before prestige-pacing: every run 237 min, tok/h 1.0 → 2.0). First token @133m in run 1 (unchanged, so the early game is), @32m by run 8. Split ~55-60% prebuilt, 10-14% custom, ~11% PC add-ons, 7-14% consoles, ~7% service; bot rating ~4.3★. Restock capacity had been the late-game bottleneck (shelves running dry): the later totals rose a lot, so `TOKEN_R0` or the token curve may want raising if tokens come too fast. Idling past 2035 (`--stop=best`) barely helps.
- **Retail seasons** (`CS.SEASONS` in data.js): January Lull, Summer Game Sale, Back to School, Black Friday, Holiday Rush, every year. `eventsAt` turns them into events with real dates (`season_<id>`, cached per year) so the Times panel, ticker, buyers' forecasts and Advisor see them; `kinds` boosts how often shoppers pick up a kind (`E.kindBoost(d, kind)`, applied in the engine's add-on loop, `CS.Con.rates` and `CS.M` modelRates; keep all three in step). The Advisor scans the next 0.3 years in 0.02 steps (seasons are short). Worth ~+2-12% revenue a run.
- **Reminders (app, `src/notify.ts`, `expo-notifications`)**: opt-in (`settings.notify`, Menu → Look; asks the OS when switched on; a one-time hint after 1 h of play); once on, a Reminders panel in Menu has a switch per kind (`settings.notifyKinds`, default all on: night shift, empty shelves, Franchise Token ready, console launch, Service Desk overloaded) and how early to announce the end of the night shift (`settings.notifyLead` minutes). On background `GameProvider` schedules local notifications from `E.remindersAt(s, { kinds, leadMin })` (core, `tools/reminder-check.js`): night shift over (at `offlineCap`), shelves empty (only without any restocking: PC stock / ~half of served shoppers), and the next console launch within the cap (offline calendar speed). On foreground all are cancelled; while the app is open the handler shows nothing (the game has its own banners). Expo applies the expo-notifications config plugin by default and it adds a push (`aps-environment`) entitlement; `app.json` sets it to `enableRemoteNotifications: false` so local-only builds don't need the Push capability. Native package: run `npm run xcode` after pulling.
- **Offline catch-up speed**: `E.offline` = `offlineStart` + `offlineRun(job, maxSteps)`; the app (`GameProvider.catchUp`) runs it in ~12 ms slices between frames with a progress overlay after 250 ms (`components/CatchUpOverlay.tsx`); the tick, autosave and background save wait while it runs, and a replaced game drops the job. Gaps over 2 h use 10 s steps (−1-3% revenue, ~40% faster). Hot path: `slotsUsed` (sizes memoised, zero-stock keys skipped) and `d.used`, the shelf space counted once per step and kept current by that step's purchases (all purchases in a step happen before sales). Module caches keyed on rounded years must compute at the bucket's year (`marketShares`, `serviceAt`), or results depend on what ran before. `tools/offline-check.js` proves sliced = one-shot. 8 h late-game catch-up: ~1.5 s → ~0.3-0.5 s in Node.
- **Decision events** (`core/offers.js`, loaded after managers.js and before advisor.js in `core/index.js` and `index.php`): every 3-6 min of live play (`calRate >= 1`, never offline; after 10 PCs sold) `CS.Offers.tick` opens one card in `s.offer` for 90 s (ignored = declined, `stats.offersMissed`). Templates `CS.OFFERS` (`make` -> params or null, `title`/`text`, two `choices` with `run`): bulk order (10% off, ~20 s of income), clearance container (−40%, needs room), reviewer (free PC; rave = +0.5★ and a 2-min +25% boost, flop = −0.3★), ad deal (6 s of income for +30% shoppers for 2 min), Y2K sticker (1999, +0.4★), crypto miner (2017-22: +30% price, −0.3★; refusing gives +0.1★). Boosts live in `s.boost` and multiply `lambda`. UI: `CS.Offers.view` / `resolve` / `activeBoost`; web card at the top of the Shop tab (`renderOffer`, `data-act="offer"`), app `components/OfferPanel.tsx` + `decide()` in `GameProvider`; both toast new offers on other tabs. `sim.js` answers with a simple policy (`--offers=decline` to compare: answering well is worth ~6-12% revenue). `tools/offer-check.js`.
- **Reputation** (`s.rep`, 1-5★, new shops 3★): drifts (600 s time constant) toward a target from four factor scores built on 120 s rate memories in `s.rate` (`srv`, `busy`, `so`): stock on the shelves (stock-outs / served, weight .35), checkout speed (walk-outs, .3), quality of PCs sold (`pcRel`, 0.8 scores 0.5, .25) and repairs (desk open and keeping up, .1). Multiplies `lambda` by 0.85-1.15 (`E.repMult`). `E.reputationView(s, d)` gives stars, label, target, effect and per-factor star cost for the Shop tab panel (web `renderReputation`, app `components/ReputationPanel.tsx`) and the Advisor's ⭐ hint; the app's Shop header shows ★. `tools/rep-check.js`. Worth ~+5-15% revenue a run.
- **Service tab + Service Desk manager:** the Service tab (web `buildService`/`renderService`, app `src/app/service.tsx`; visible once the desk is available) holds the desk panel, a manager summary and all `Service` upgrades (taken out of the Upgrades tab: web `renderUpGroup`, app `buildUpgradesView(s, filter, groups)` + exported `UpgradeCard`). The manager is a `MGR_CATS` entry `svc` (flags `designer` + `svc`, i.e. not a stock buyer): `svcTick` every `SVC_EVERY` (45 s, faster with Speed) buys the cheapest `svc` upgrade that closes the gap between repair capacity and walk-ins × (1 + headroom + 3%·Planning), up to 1 + Speed/3 per review, within `maxSpendPct` of cash above `reserveCash`, and keeps buying Warranty Pitch; Haggling refunds 0.5% per level; presets `CS.SVC_PRESETS`. Its wage is normal manager upkeep. Settings spec `SVC_SPEC` (web `js/ui.js`, app `buyers.ts`). Checked in `tools/service-check.js`.
- **Service Desk** (`svc_desk`, 1994; Upgrades group `Service`): walk-in repair jobs = `lambda × SVC_SHARE (0.18) × menu mix`, done up to `svcCap` (owner 0.04/s + `svc` upgrades: technician, diagnostic bench, remote line, AI triage), paid at the era's average service price (`CS.SERVICES`, inflated, × `d.profit`). Extended warranties: 12% + 3%/level of Warranty Pitch (max 8) of PC buyers pay 12% of the price inside `sellUnits`; 40% of that goes to `s.claims`, paid out with a 900 s time constant before upkeep. Repairs and warranties count as revenue (tokens). Events: `SVC_ITEM` (k jobs) and `WARRANTY_ITEM` (k 0 = log line only). `E.serviceView(s, d)` is the panel's data for both UIs (Shop tab: web `renderService`, app `components/ServicePanel.tsx`). Advisor values `svc_desk` / `svc` / `warranty`; `tools/service-check.js`. Worth ~9% of revenue in sim (repairs ~5%, warranties ~3.5%).
- **Hustle** (`E.hustle`): cooldown `E.HUSTLE_CD` (3 s). A hustle within 4 s of the cooldown ending continues a streak (max 10, `E.hustleStreak(s)` for the UI 🔥): +3% buy chance per level. A sale is a business order sized to ~4 s of current income (+0.5 s per streak level), capped by stock; add-ons scale with it. `sim.js --hustle` (always hustling) earns ~+60% revenue and the first token ~30 min sooner.
- **Franchise/HQ**: reset to claim Franchise Tokens (late game), spend on persistent HQ upgrades (`t_*` ids, including buyer upgrades `t_mgr*`). **Time Warp** (`t_warp`, `E.calSpeed`): +15% calendar speed per level, only before `C.WARP_UNTIL` (2015), because the last decade earns most of a run and a full-calendar warp *lowered* tok/h in sim. **Head Start** (`t_head`, `C.HEAD_STARTS`, `E.startYear`): new franchises open in 1996 / 2000 / 2005 with $60K / $400K / $2.5M extra. Opening upgrades (`t_cash`, `t_kit`, `t_mgr_office`, `t_head`) go through `startBonus()`; a new franchise has `s.fresh = true` until its first sale, and HQ buys in that window apply immediately (otherwise they wait for the next franchise). Checked by `tools/hq-check.js`.
- **Restock upgrades** (kind `restock`: Stock Clerk 1993 → Conveyor Stock Room 1997 → Forklift Crew 2000 → Pallet Racking 2007 → Robotic Fulfilment 2015 → Storage Grid 2021 → Drone Docks 2027 → Supply Swarm 2032, each per-unit-second pricier than the last) plus Loading Dock Scheduling (`restockMult`, +8% from every crew; `d.restock` = sum × multiplier, which buyers' order rate also uses). The Advisor values the multiplier when orders are slower than sales; the sim bot buys it.
- **Buyer orders:** add-ons (games, accessories, console games/accessories) are ordered in packs, one order (= one unit of the buyer's order budget `s.mAcc`) per pack; `restock` orders as many packs as the gap needs. It used to order one pack per item per step, which capped a best-seller at ~10 units/s (a tenth of that in 10 s offline steps) and kept add-ons at ~3% of revenue.
- **Managers** (`core/managers.js`): categories `pre, bp, game, acc, con` + `design`. Skills forecast/negotiate/logistics, traits, presets, per-category cfg, velocity EMAs, `decide()` every 15 s, own order budget, wages in upkeep, pins/skips from the Stock tab, notebook log.
- **PC Designer** (`design` category, `designTick`): picks among 8 concepts using modelled profit gain over the current lineup; auto-prices (Market sense ≥2), sets targets when no Custom Builds buyer, retires obsolete designs, design fee = 12× unit cost; Engineering adds `0.01*level` to `customBonus`. Blueprints it creates carry `bp.by='designer'` (Workshop shows tag + "Take over").

## Versioning & change log popup
- `version.json` (`major.minor.build`): the build number auto-increments on **every commit** via `.githooks/pre-commit` -> `tools/bump-version.js`. Enable once per clone: `git config core.hooksPath .githooks` (the hook does nothing if not enabled; run `node tools/bump-version.js` by hand before a deploy). Bump `major`/`minor` by hand for big releases. If two branches both bump, resolve the `version.json` conflict by taking the higher build and bumping again.
- **Web ↔ app parity (2026-10-26):** the website has the app's visual extras: performance/demand meters on item cards (`.meters`, same scales as the app: performance 150% fills the bar), level bars on upgrade cards (`.lvbar`), progress bars on locked trophies (`a.p(S)`), emoji on panel titles, the ★ shop rating and a year-progress bar in the header (`#repChip`, `#yearBar`), and the sliced offline catch-up with a progress sheet (`goOffline`: `E.offlineStart/offlineRun` in ~12 ms slices, `#catchup` after 250 ms; `catching` blocks the tick and every save while it runs; the welcome-back and What's new sheets wait for it). App-only by nature: Game Center, haptics, push-style reminders. Test in a real browser with Playwright-core + system Chrome against the local test backend (see Testing); CPU throttling (`Emulation.setCPUThrottlingRate`) makes the catch-up sheet show.
- **Same number everywhere:** `tools/sync-release.js` (run by `bump-version.js` and so by the hook; `--check` runs in CI) copies `version.json` + `changelog.json` to `app/src/release.json` and sets `expo.version` in `app/app.json` to `major.minor.build`, so the website and the app show one version. The app shows it in Menu → About (`src/config.ts` `APP_VERSION`) and shows unseen release entries after an update (`WhatsNewGate` / `WhatsNewModal`, last seen build in AsyncStorage `csig-seen-build`; an existing player's first run shows only the latest entry). **After adding a changelog entry run `node tools/sync-release.js`** (the hook does it on commit when enabled: `git config core.hooksPath .githooks`; without the hook entries stay `"build": "next"` and never show in What's new, which is how 16 entries piled up before 2026-10-25, when they were numbered by hand).
- `changelog.json`: player-facing release notes, newest first. **For every feature/fix, add an entry with `"build": "next"`**; the hook stamps it with the real build number and date on commit. Friendly wording, one short line per change.
- `index.php` injects both files into `window.CSIG` (`version`, `changelog`). `maybeShowWhatsNew` in `js/ui.js` pops up entries newer than `localStorage['csig-seen-build']` (max 5) after launch, waits for the welcome-back report to close, and shows only the latest entry to existing players on first run. Menu -> About shows the version and a "What's new" button.

## Gotchas
- Restock/build accumulators must be capped with `Math.max(6, rate*dt*2)`, not a fixed small number, or fast shops stall.
- UI lists use `syncList` keyed diffing; only disable `tgt` buttons on cards (pin/skip buttons are separate).
- Number formatting rollover (`num()` must not print "1000K").
- Closed `<details>` hide controls from Playwright — open them in tests; wait for init after reloads.
- Sandbox: MariaDB/php servers die between turns. Restart: `mysqld_safe --bind-address=127.0.0.1 &`, `php -S 127.0.0.1:8124 -t . &`, then `php tools/install.php`. Clean smoke users with `DELETE FROM users WHERE username LIKE "smoke%"`.
- **API auth:** `api_guard()` accepts either the website's cookie + CSRF, or `Authorization: Bearer <token>` / `X-Api-Token: <token>` (no CSRF). **IONOS strips `Authorization`** (checked against production with a fake token: Bearer -> `not_logged_in`, `X-Api-Token` -> `bad_token`), so the app (`src/api.ts`) sends both headers. To re-check a host without credentials: POST `{}` to `api/load.php` with a fake 64-hex token in each header; `bad_token` means PHP saw it. A bearer token present but invalid is rejected, never silently downgraded to the cookie. Tokens are stored as SHA-256 only (`api_tokens`), 180-day sliding expiry, max 10 per user. Sign-ups through the API are limited per IP (`register_max_per_ip_hour`, default 5) using `login_attempts` rows with username `@register`.
- **Sign in with Game Center (iOS app):** `inc/gamecenter.php` (`gc_verify`: Apple's identity signature over teamPlayerID ‖ bundle id ‖ UInt64BE ms timestamp ‖ salt, certificate fetched over HTTPS only from `static.gc.apple.com` / `sandbox.gc.apple.com` and cached a day in the temp dir, ≤15 min old, each signature once via `gc_proofs`), `users.gc_player_id` (unique) + `users.has_password` (`sql/upgrade_005_game_center.sql`). Endpoints `auth_gamecenter.php` (sign in or create; new accounts get a username from the display name + digits and no password), `auth_gc_link.php` (link / unlink; unlinking needs a password), `auth_set_password.php` (first password without the old one when `has_password` = 0); `auth_delete.php` takes a fresh proof instead of a password for such accounts. Every auth reply's user has `gameCenter` / `hasPassword` (`auth_user_payload`). Native: `identityProof()` in `modules/game-center` → `gcProof()` (`src/gamecenter.ts`) → `AuthProvider.signInGameCenter / linkGameCenter / unlinkGameCenter / setPassword`; Account panel shows "Continue with Game Center" when signed out and Game Center is signed in. Test with `tools/api-gc-smoke.js` (its own RSA key; server config `gc_test_public_key` = the key file, never in production). Real Game Center needs the Apple Developer account (sandbox player on a dev build).
- **Password reset / email:** `users.email` is optional (unique, stored lowercased; the API only ever returns it masked, `d***@host`). Reset tokens live in `password_resets` (SHA-256 only, 1 h, single use, max 3 per account per hour, 5 requests per IP per hour via `login_attempts` rows `@forgot`). `inc/reset.php` (tokens, emails, throttles) + `inc/mail.php` (own minimal SMTP client: STARTTLS + AUTH LOGIN, no Composer; `mail_transport` `'log'` writes to `mail_log` for tests; `smtp_verify_peer` false only for self-signed test servers). `reset_token_status()` tells a cut-off link (`malformed`, with how many characters arrived), an unknown, already-used or expired one apart, and the reset page says which (it used to say "invalid or has expired" for all of them); tokens are cleaned (`clean_reset_token`: case, spaces, line breaks, trailing dots) before checking, refusals are logged without the token, and the emailed link is `https://` for any real domain even when PHP can't see HTTPS. Endpoints `api/auth_forgot.php` (never reveals whether an address exists) and `api/auth_set_email.php` (needs the password); pages `forgot.php`, `reset-password.php`; a successful reset revokes all API tokens and sends a confirmation. Production needs `mail_from`, `smtp_user`, `smtp_pass` in the server-only `inc/config.php` (IONOS: `smtp.ionos.com:587`, mailbox `admin@davideis.com`). Check with `node tools/api-reset-smoke.js` (see Testing below). App: `AuthModal` has a Forgot-password mode and an optional email on sign-up; `AccountPanel` has Add/Change email.
- **Session before output (account pages):** `page_head()` starts the session first. Hosts that don't buffer output (shared hosting often) cannot start one after the page began printing, so the form's CSRF token never matches ("Your session expired" on forgot / reset-password). Test the backend with `php -d output_buffering=0 -S ...` so that mistake shows up locally (Homebrew PHP buffers and hides it).
- **Testing the backend on a Mac without touching the dev DB:** `mariadb-install-db --datadir=<dir> --auth-root-authentication-method=normal`, then `mariadbd --datadir=<dir> --port=3399 --bind-address=127.0.0.1 --socket=/tmp/csig-test.sock` (macOS socket paths are limited to ~100 chars, so keep the socket in /tmp); copy the repo (minus `.git`, `app`, `node_modules`) to a scratch dir with its own `inc/config.php` (raise `register_max_per_ip_hour` and `login_max_per_ip` for repeated runs), run `php tools/install.php` and `php -S 127.0.0.1:8125`, then both smoke scripts.

## Native app plan
React Native (Expo) app reusing the simulation: `engine.js`, `data.js`, `addons.js`, `consoles.js`, `managers.js`, `advisor.js` move into a DOM-free shared `core/` module (imports instead of `CS.*` globals); only `ui.js` is rewritten as native components. Backend stays PHP + MariaDB with bearer-token auth and an in-app delete-account endpoint (done, see README "Native app API"); no CORS needed (React Native is not a browser). Keep `tools/sim.js` and the `*-check.js` scripts working against `core/`.

### `app/` (Expo, SDK 58, TypeScript)
- Run: `cd app && npm install && npx expo start --ios`. Checks: `npx tsc --noEmit`, `npx expo-doctor`, `npx expo export --platform ios` (proves Metro + Hermes can bundle `core/`).
- Expo Router (file routes in `src/app/`: tabs Shop/Stock/Upgrades/Workshop/Buyers/HQ/Menu; `@/` aliases `src/`). `src/GameProvider.tsx` owns the sim: loads the save, offline catch-up (`E.offline`, gaps >= 60 s, welcome-back sheet), 250 ms tick, autosave every 15 s + on background. `src/storage.ts` = AsyncStorage (`csig-save-v1`). `metro.config.js` watches `../core` and aliases it as `@core`; `src/game.ts` wraps `CS.E`; `src/core.d.ts` declares the untyped module. Add packages with `npx expo install <pkg>` (SDK-compatible versions). Expo APIs change per SDK, so check https://docs.expo.dev/versions/ before using one.
